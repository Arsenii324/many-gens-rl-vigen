# Brief D — Evaluation Protocol Audit for the RL-ViGen / robosuite Visual-RL Generalization Benchmark

## TL;DR
- **A faithful reference protocol DOES exist in RL-ViGen's own paper and code, and it contradicts the brief's central premise on two points**: (1) RL-ViGen's robosuite "eval" scenes are a *separate* randomized set from the single clean training scene, so the §2 "1/10 in-distribution contamination" is almost certainly a scene-label collision, not a real bug; (2) RL-ViGen reports *raw episodic return*, uses a *deterministic* policy, evaluates the *final* checkpoint, and runs 100 episodes (10 scenes × 10 trials) — meaning three of the project's contested choices already match the reference. The mean-vs-IQM defence, by contrast, is a level confusion and should be dropped.
- **The single most important correction is the headline metric**: on robosuite's fixed-horizon, no-early-termination, shaped-reward tasks, episodic return rewards proximity-holding rather than task completion; success rate (from robosuite `_check_success`) should be the headline, with return as a secondary diagnostic. This is the project's biggest live risk and it is cheap to fix now.
- **A pairwise-significant 12-arm ranking is NOT affordable at this budget**, and you should not attempt one. Because training (~2–3 h/run) dwarfs evaluation (~11 min/100 episodes), cutting episodes barely saves compute; the real lever is runs. The affordable, defensible design is 3 seeds × 2 tasks × 12 arms + random control, report P_train and P_eval as two columns with a derived gap, a measured random floor + competence gate, rliable stratified-bootstrap 95% CIs, and **tiered/banded rankings** — never a fully-ordered significant leaderboard.

## Key Findings

1. **RL-ViGen's robosuite evaluation protocol is fully documented** (NeurIPS 2023 supplementary §B and §D.1.1): "each difficulty level comprises 10 distinct scenes. We perform 10 trials for each of these scenes (100 trials in total)." The headline metric is **raw episodic return averaged over the three tasks** ("The aggregated return is calculated by averaging over all three tasks"); the code (`eval.py::robo_eval`) accumulates `time_step.reward` and never reads a success flag. Evaluation is **deterministic** (`agent.act(..., eval_mode=True)`, the DrQ-v2 mean-action convention) and uses the **final** checkpoint (`snapshot.pt` is overwritten periodically; there is no best-by-eval selection). Action repeat is **1** for robosuite (Table 2). **The brief's premise that "we were never given a reference evaluation to copy" is therefore false in substance** — a reference protocol exists in the paper and code, and the withdrawn candidate the supervisor rejected was not the only source.

2. **The §2 contamination concern is a misreading of scene indexing.** In the upstream SECANT API `make_robosuite(task, mode, scene_id)`, `mode="train"` is a single clean scene (scene_id fixed at 0) and each `mode="eval-easy"/"eval-hard"/"eval-extreme"` is its *own* set of 10 randomized scenes indexed 0–9. RL-ViGen's `robo_eval` loop switches `scene_id` 1→9 only in eval mode and does not switch in train mode. So "eval-easy scene 0" is a randomized easy scene, **not** the clean training scene — there is no in-distribution scene in the eval-easy set. The 0–9 label appears in both regimes but under different `mode`; that is a label collision, not shared scenes.

3. **Mean vs IQM is a level confusion.** In Agarwal et al. (NeurIPS 2021), "Also called 25% trimmed mean, IQM discards the bottom and top 25% of the *runs* and calculates the mean score of the remaining 50% runs (=⌊NM/2⌋ for N runs each on M tasks)." IQM therefore aggregates over runs (task×seed scores), never over episodes within a run. The project's evidence (bimodal *episode* returns, mean/IQM ratio 1.418) is measured at the wrong level and does not bear on run-level IQM. Nobody proposes trimming episodes.

4. **Return is the wrong headline for these tasks.** The robosuite documentation states verbatim: "robosuite environments do not terminate if a success criterion is reached, but always continue for a fixed number of timesteps, determined by the horizon argument. This is a standard design decision for reinforcement learning in robot manipulation domains." Combined with a dense reaching reward `1 − np.tanh(10.0 · dist)` paid every step (confirmed in robosuite source; the range issue is discussed in ARISE-Initiative/robosuite Issue #130), a policy that hovers near the object for 500 steps without ever lifting accumulates large return. Success rate from `_check_success` is the accepted headline across robosuite's own benchmarking, RoboMimic, ManiSkill, Meta-World and GR00T.

5. **SGQN aux lr in RL-ViGen's Table 6 is 8e-5 for all three robosuite tasks** (and 8e-5 also appears in the CARLA, Habitat and Adroit tables), versus canonical SGQN (Bertoin, Zouitine, Zouitine & Rachelson, NeurIPS 2022, arXiv:2209.09203), which uses a larger auxiliary learning rate. Whether the shipped code actually applies 8e-5 or a constructor default (the project suspects `aux_lr=0.3`) could **not be confirmed** — the SGQN agent source and config files were not retrievable. This remains the one open runtime hazard and should be resolved by direct code inspection before compute is spent.

## Details

### Output 1 — Critique of §1, choice by choice

**Training regime = `train`, scene 0 only.** Correct and matches the reference. RL-ViGen and SECANT both train on a single clean scene and test zero-shot on the perturbed distributions (RL-ViGen Figure 2: "Stage 1 … fixed scenario," "Stage 2 … tested across various visual generalization scenes in a zero-shot manner"). No change.

**Evaluation regime = `eval-easy`.** Defensible; `eval-easy` is the mildest held-out distribution and the one where RL-ViGen itself reports the clearest separation (supplementary Figure 19, "Robo EASY"). Note RL-ViGen's own robosuite table used **Door = Easy, Lift = Medium** difficulty (Table 6, "Level"), so your regime labels should be checked against theirs if you intend any comparison to their numbers.

**Evaluation scenes 0–9 including the training scene.** This is the weakest stated point, but the premise is likely false — see Output 2. If your custom evaluator sets `mode="eval-easy"` for all ten scene ids, there is no contamination. Verify one line in your `robo_wrapper`.

**Episodes per scene 10 → 100 total.** Exactly matches the reference (10 trials × 10 scenes). Statistically 100 episodes is more than enough to pin a per-seed *return* mean (see Output 5), and *fewer* than enough to resolve success-rate differences below ~10 pp. Keep 100 if you adopt success rate; you may drop toward 30 for a return-only pilot, but it barely changes compute.

**Deterministic policy.** Matches the reference (DrQ-v2 `eval_mode=True` = mean action) and is the correct, comparable rule *provided it is implemented uniformly as "take the distribution's mean/mode, no sampling."* This is fair across the DDPG-style arms (mean action is native), the SAC-style arms (mean of the squashed Gaussian), and the PPO-Gaussian arms (mode of the Gaussian; identical to Stable-Baselines3 `deterministic=True`, whose `evaluate_policy` defaults to `deterministic=True`). The asymmetry to watch: a deterministic-policy-plus-noise agent (DrQ-v2) evaluates at its policy mean with zero added noise, whereas a Gaussian agent evaluates at its mean and *discards* learned entropy. For converged policies this is the standard, accepted convention and does not systematically advantage either family; document it explicitly in the frozen dataclass and require the opaque `policy` wrapper to expose a deterministic mode. No change.

**Metric = raw undiscounted return, never normalized.** This matches RL-ViGen's robosuite path (which reports raw averaged return, not the normalized cross-environment score), so it is faithful to the reference. But it is the choice most likely to mislead on *these* tasks — see Outputs 3 and 4. Recommendation: keep raw return as a recorded quantity, but promote **success rate to the headline**. Your instinct against normalization is sound for the *reported* number; it does not remove the need for a floor when you compute a gap.

**Aggregation = mean, not IQM.** The stated justification does not survive scrutiny (Output 3). At the *episode* level, do not trim — mean (or success proportion) is correct. At the *run/seed* level, IQM is the field standard, but with 3–5 seeds IQM trims to essentially the median seed and loses meaning; report the mean plus rliable stratified-bootstrap CIs plus per-seed points. So: right answer (mean within run) for the wrong reason; wrong claim (mean superior to IQM across runs).

**Uncertainty = bootstrap 95% CI.** Correct and matches best practice (Agarwal et al. 2021 recommend percentile/stratified bootstrap CIs, computed with ~2000 resamples over seeds). Upgrade to **stratified** bootstrap (resample within task strata) once you aggregate across Door and Lift. No change in spirit.

**Gap = absolute difference train − eval, never a ratio.** The anti-ratio rule is well-founded (Output 4). But an absolute gap is not comparable across arms of different competence, and a non-learner gets gap ≈ 0. Add a floor-normalization and a competence gate rather than reporting a bare difference.

**Checkpoint = final, never best-by-eval.** Correct and matches the reference exactly (RL-ViGen saves and loads a single overwritten `snapshot.pt`; best-by-eval would leak the test set into model selection). No change.

**Success recorded alongside return.** Keep — and then make it the headline.

### Output 2 — Verdict on including the training scene

**Verdict: do not treat this as a bug; it is almost certainly a scene-label collision, but confirm it in your own wrapper with a one-line check.** Upstream evidence is consistent and primary: SECANT's `make_robosuite` uses `scene_id=0` for `mode="train"` and `scene_id∈0..9` for eval modes, each eval difficulty being an independent 10-scene randomization; RL-ViGen's supplementary confirms "each difficulty level comprises 10 distinct scenes," and RL-ViGen's `robo_eval` only sweeps eval scenes. Therefore "eval-easy scene 0" is a perturbed easy scene, not the clean training scene, and there is no in-distribution episode in the eval mean.

On the literature norm you asked about:
- **Procgen** (Cobbe et al. 2020) trains on N levels (easy: 200 levels / 25M steps; hard: 500 levels / 100–200M steps — confirmed by the openai/train-procgen flags `--num_levels 200 --distribution_mode easy` and `--num_levels 500 --distribution_mode hard`, and by the Impoola reproduction, arXiv:2503.05546) and **tests on the full distribution of levels**. This formally *can* re-draw a training level, but from a space so large the training levels are a measure-zero contamination; the community treats this as clean held-out testing.
- **DMC-GB** (Hansen & Wang) trains in one fixed environment and evaluates on disjoint test distributions (color_hard, video_easy/hard); PAD (Hansen et al. 2020) additionally reports "the unmodified training environment" as a *separate* condition, not blended into the test mean.
- **RL-ViGen** itself reports training-scenario and testing-scenario performance in separate figures.

So the accepted structure is: **train and test are disjoint, and any in-distribution number is reported as its own column, never averaged into the generalization mean.** If your custom evaluator does map its "scene 0" to the clean training condition, remove it from the eval mean and report it as the P_train column you need anyway for the gap. Cost of the fix is zero now and unbounded later (the hash re-pools everything).

### Output 3 — Mean vs IQM vs success rate

**On mean vs IQM: your reasoning is unsound, but the practical answer is close to what you do.** IQM (Agarwal et al. 2021) is a 25%-trimmed mean over *runs* — the (task, seed) scores — not over episodes. Your evidence about bimodal *episode* returns and a mean/IQM ratio of 1.418 is measured at the episode level, which no one trims. Recommendation: within a run, aggregate episodes by the plain mean (for return) or the success proportion (for success) — do not trim. Across seeds, follow Agarwal: report IQM with stratified-bootstrap 95% CIs as the primary aggregate, but because you will have only 3–5 seeds (where IQM trims to the middle 1–2 seeds and carries little information), also show the mean and all per-seed points. Present both; do not claim mean is superior.

**On success rate vs return: make success rate the headline. This is the correction we most endorse.** robosuite's design — no early termination, full 500-step horizon, dense `1 − tanh(10·d)` reaching reward every step — means return ranks *proximity-holding*, not competence, and a proximity-holder can outscore an intermittent succeeder. Manipulation benchmarks overwhelmingly headline success rate (robosuite's own SAC benchmarking, RoboMimic — "average success rate across 100 evaluation episodes" — ManiSkill, Meta-World, and GR00T N1 — "average success rate over 100 trials, taking the maximum score of the last 5 checkpoints"). Report success rate as headline and return as a secondary diagnostic; you already record both. robosuite exposes `_check_success` per environment ("The binary success check that is used to compute the sparse reward is implemented in the `_check_success` method of each environment class" — Lift: cube lifted above a height threshold; Door: hinge angle past a threshold), and it can be polled every step to log "success-at-any-step" and "success-at-final-step."

**Consequence for episode count (this may *raise* it):** success rate is a Bernoulli proportion, so its precision is set by episode count, not seed count. Using the Wilson score interval (half-width ≈ z·√(p(1−p)/N)):
- to pin a single arm's success rate to ±5 pp at 95% around p = 0.7 needs **N ≈ 380 episodes** (confirmed by the PhAIL VLA-benchmark derivation, which gives "N ≈ 380 rollouts" for exactly this case);
- at N = 100, the 95% Wilson interval on an observed 0.7 is roughly [0.60, 0.78];
- at N = 30 it is roughly [0.52, 0.84] — too wide to rank.
- To *separate two arms* 10 pp apart (e.g. 0.5 vs 0.6) at 80% power, two-sided α = 0.05, you need **≈ 390 episodes per arm** (n ≈ 2·(1.96 + 0.84)²·p̄(1 − p̄)/δ²). 100 episodes only resolves gaps of roughly ≥ 20 pp.

So if success rate is the headline and you want 10-pp resolution, 100 episodes is *too few*, not too many — but you resolve that by pooling episodes across seeds (3 seeds × 100 = 300) and by reporting ties honestly, not by inflating per-point episodes.

**Secondary metrics when success ≈ 0 (a real risk on Lift at 500k frames):** report a graded competence signal that robosuite state exposes — fraction of episodes with a successful grasp, max block height achieved, and time-to-first-grasp. These degrade gracefully to zero and let you rank arms that never complete the task.

### Output 4 — Recommended gap definition (including never-learned methods)

**Definitions in the literature.** Kirk, Zhang, Grefenstette & Rocktäschel, "A Survey of Zero-shot Generalisation in Deep Reinforcement Learning," JAIR 76:201–264, 2023 (doi:10.1613/JAIR.1.14174), frame the generalization gap as the difference between train and test performance; Procgen reports train and test *normalized* scores separately (min-max via (R − Rmin)/(Rmax − Rmin)) and reads the gap off the two; DMC-GB reports test return, sometimes alongside train. The three candidate forms and their failure modes:
- **Absolute difference (train − test):** simple, but not comparable across arms of different competence, and a non-learner scores ≈ 0 (false "perfect generalizer").
- **Ratio / retention (test/train):** blows up at small denominators — exactly your 131.3% off a 0.11 denominator disaster.
- **Normalized retention (min-max):** robust if the floor is measured.

**Recommendation.**
1. **Report P_train and P_eval as two separate columns and derive the gap** — this is the accepted presentation (Procgen does exactly this) and lets a reader see whether a small gap reflects real robustness or a failure to learn. Do not collapse to a single number.
2. **Normalize both by a measured random floor:** define normalized score = (P − P_random)/(P_reference − P_random), where P_random is your uniform-random control (you already run it) and P_reference is the best training-regime score achieved by any arm at this frame budget (a benchmark-relative "expert" stand-in, since no true expert exists at 500k frames). Report the gap as the difference of normalized scores. This is the Atari-human-normalized / Procgen-min-max approach adapted to a no-expert setting.
3. **Competence gate:** require P_train's CI to exclude the random floor before a gap is reported. This is not an ad-hoc invention — Jiang, Raileanu et al., "On the Importance of Exploration for Generalization in Reinforcement Learning" (NeurIPS 2023), state it directly: "Without good training performance, the generalization gap is not a meaningful measure: a random policy would have no generalization gap at all." An arm whose training performance is statistically indistinguishable from random is labelled "did not learn," and its gap is left undefined rather than printed as ≈ 0.
4. **Fixed-budget vs matched-performance:** matched-performance comparison is more informative but expensive (it requires interpolating each arm to a common P_train). The cheap approximation is to exploit the checkpoints you already save along training: plot the eval score as a function of train score using the periodic snapshots, so the reader can read off the gap at a matched train level without extra runs. Headline at a **fixed frame budget** (cheapest, matches RL-ViGen), and offer the gap-vs-train-score curve as the matched-performance approximation.

### Output 5 — Minimum viable design, grounded in T4-hours

**Compute anchors (from the brief):** ~78 env steps/s on one T4; 500-step episode = 6.4 s; 100 eval episodes ≈ 11 min; a 500k-frame run ≈ 1.8 h of pure stepping. **Note a discrepancy to resolve:** RL-ViGen's Table 6 trains **Door at 6e5 and Lift at 8e5 frames**, not 500k — at 78 steps/s that is ~2.1 h and ~2.85 h respectively. Budget with your own frame counts, not 500k, or you will under-provision Lift by ~60%.

**The decisive arithmetic:** training dominates. A run is ~1.8–2.85 h of training plus ~11 min per 100-episode eval point. Evaluating all three regimes (train, eval-easy, eval-hard) once at the end adds ~33 min. So **eval is ~15–25% of a run; cutting episodes from 100 to 30 saves ~7 min out of ~2.5 h — negligible.** The lever is the number of runs (seeds × tasks × arms), not episodes-per-point. Keep 100 episodes (you need them for success-rate resolution) and spend your savings on seeds instead.

**Full matrix costs (13 policies incl. random control × 2 tasks, end-only eval of 3 regimes, per-run ≈ 2.5 h avg):**
- 3 seeds: 13 × 2 × 3 = 78 runs × 2.5 h ≈ **195 T4-hours ≈ 8 days on one T4, ~4 days on two.**
- 5 seeds: 130 runs × 2.5 h ≈ **325 T4-hours ≈ 13.5 days on one T4, ~7 days on two.**
- Intermediate-checkpoint learning curves (eval every 50k ≈ 10 points) add ~5 h/run of eval and roughly *triple* total cost — do this only for a 2–3 arm illustrative subset, not the whole matrix.
- Adding `eval-hard` is already included above (it is one extra 11-min eval point per run); `eval-extreme` is another 11 min. Affordable. The expensive axis is seeds and arms, not regimes.

**What is claimable at each seed count (the honest part):**
- With **66 pairwise comparisons** (12 arms), a Bonferroni-corrected α = 0.05/66 ≈ 7.6e-4 inflates the required sample by ~2× over uncorrected. Two-sample power (n ≈ 16/d² per group, two-sided α = 0.05, power 0.8) says d = 1 needs ~17 seeds/arm, d = 1.5 ~8, d = 2 ~5 — *before* the ~2× multiple-comparisons penalty. Given the large between-seed variance typical of visual RL (Henderson et al. 2018 showed non-overlapping learning curves from seed alone; Agarwal et al. 2021 report >50% Type-I error from 5-run point estimates on Atari 100k, and that "50–100 runs are needed for statistically defensible improvements with median scores"), **a pairwise-significant full ranking of 12 arms is not affordable at 3, 5, or even 10 seeds.**
- **At 3 seeds** you can credibly claim: which arms clear the random-floor competence gate; gross tiers whose rliable stratified-bootstrap CIs do not overlap; and directional gap statements where an arm's gap CI excludes zero. You cannot claim a total order.
- **At 5 seeds** the aggregate IQM/mean CIs tighten enough to defend a 3–4 band tiering and a few individual pairwise separations for large effects.
- **10 seeds** is the Procgen/DMC-GB norm (both typically report mean ± std over 5–10 seeds) and buys defensible aggregate ordering, still with overlapping-CI caveats for adjacent arms.

**Recommended minimum viable design:**
1. **Pilot first: 3 seeds, Door only, all 13 policies, eval-easy + train regimes, 100 episodes, success rate + return.** Cost ≈ 13 × 3 × ~2.2 h ≈ **86 T4-hours (~3.6 days/1 T4, ~1.8 days/2).** This gates the go/no-go decision: it tells you (a) how many arms clear the competence gate at your budget, (b) the between-seed SD you actually face (plug into the power formula to size the full run), and (c) whether Lift needs more than 8e5 frames to get any successes.
2. **If the pilot shows ≥ ~6 arms clearing the gate and between-seed SD small enough that d ≥ 1.5 tiers separate, scale to 3 seeds × 2 tasks × 13 policies** (~195 T4-h) and report banded rankings.
3. **If the pilot shows most arms at the floor on Lift, cut the matrix**: drop Lift, or drop the on-policy PPO family if it fails to learn at this budget (PPO from pixels at ~500k–800k frames on manipulation is the highest-risk arm), and reallocate to 5 seeds on Door so the aggregate claim is defensible.

**The strongest claim that IS affordable, phrased for reviewers:** *"Under an identical, hash-frozen, opaque-policy evaluation (deterministic actions, final checkpoint, 100 episodes over 10 held-out easy scenes, N seeds), we report per-arm training and eval-easy success rate with rliable stratified-bootstrap 95% CIs and a random-policy competence gate. We make no total-order claim; we report a tiered ranking in which tier boundaries correspond to non-overlapping bootstrap CIs, and we report per-arm generalization gaps only for arms that clear the competence gate, with CIs on the gap."* Reviewers accept tiered/interval claims with few seeds (this is exactly the rliable prescription); they reject unqualified leaderboards.

## Recommendations

1. **Do not re-hash the protocol for the training-scene issue — instead spend ten minutes confirming scene indexing in your own `robo_wrapper`.** If `mode="eval-easy"` is set for all ten scene ids, close the §2 concern as a label collision. If your code maps scene 0 to the clean training condition, remove it from the eval mean and move it to a P_train column. *(Trigger to change: your wrapper builds the clean training scene under an eval scene id.)*
2. **Change the headline metric to success rate before any real compute.** Keep return as a secondary column. Add grasp-fraction, max-height and time-to-first-grasp as graceful-degradation metrics for Lift. *(Trigger to keep return-only: if a pilot shows success rate is non-zero and rank-consistent with return across all arms — unlikely given the shaping.)*
3. **Drop the "mean beats IQM" justification from your docs.** Aggregate episodes within a run by mean/success-proportion (no trimming); across seeds report IQM + mean + per-seed points + stratified-bootstrap 95% CIs.
4. **Adopt the two-column P_train / P_eval presentation with a measured random floor and a competence gate**; report gaps only for arms clearing the gate; never a ratio; offer the gap-vs-train-score curve from saved checkpoints as the cheap matched-performance view.
5. **Run the 3-seed, Door-only, 13-policy pilot (~86 T4-hours) first and let it gate the full matrix.** Do not commit to a pairwise-significant 12-arm leaderboard — it is unaffordable at any seed count you can reach. Commit to tiered rankings with interval estimates, which reviewers accept.
6. **Resolve the SGQN `aux_lr` value from source before committing the one-line fix** — the paper says 8e-5, canonical SGQN uses a larger value, and the shipped default is unconfirmed. Do not assume; read `algos/sgqn.py` and the SGQN config.
7. **Budget with RL-ViGen's real frame counts (Door 6e5, Lift 8e5), not 500k.**

**The decision this feeds — whether to change the protocol before spending real compute:** Yes, make three cheap changes now (headline metric → success rate; drop the mean-vs-IQM claim; two-column gap with floor + competence gate), confirm one line (scene indexing) and one value (SGQN aux_lr), and do **not** change the deterministic-policy, final-checkpoint, 100-episode, or raw-return-recording choices — those already match the faithful reference. Then run the pilot before the full matrix.
