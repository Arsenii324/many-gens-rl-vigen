# Brief C — Porting Discrete On-Policy Generalization Methods to a 7-D Gaussian Policy

## TL;DR
- **All four arms are reportable, but only under explicit "unvalidated continuous adaptation" caveats, and two design defaults must be fixed first** — the on-policy family's γ=0.999 contradicts IDAAC's own continuous configuration (γ=0.99, verified verbatim in the paper's Appendix E), and the 8-samples-per-minibatch rollout is below any published regime and must be raised to num_steps=2048 with num_mini_batch=32.
- **A continuous PPG reference exists but is unvalidated** (XuanCe `Gaussian_PPG`); **no continuous IBAC-SNI or CTRL implementation exists anywhere we searched**, so those two are original engineering with no reference to check against and are the genuine renegotiation-risk arms.
- **The rollout-size problem dominates everything.** IDAAC's own DMControl config (2048 steps × 1 process) legitimizes num_envs=1, so fix batch size by raising num_steps, not by building subprocess parallelism — but this is only clearly defensible for IDAAC/DAAC; CTRL's Sinkhorn clustering and PPG's auxiliary cadence degrade at small batch and few updates.

## Key Findings

**1. IDAAC's continuous configuration is fully documented and contradicts the current setup.** The ICML 2021 supplementary (Raileanu & Fergus, Appendix E) states verbatim: "We use γ = 0.99, λ = 0.95 for the generalized advantage estimates, 2048 steps, 1 process, value loss coefficient 0.5, and linear rate decay over 1 million environment steps." The grid search found "10 ppo epochs, 0.0 entropy coefficient, 0.0003 learning rate, and 32 minibatches to work best." Per-method: "for PPG ... Nπ = 32, Eπ = 1, EV = 1, Eaux = 6, and βclone = 1"; "for DAAC and IDAAC ... EV = 9, Nπ = 32, αa = 0.1, and αi = 0.1." Every number in the prior scoping pass checks out. **The single most important consequence: γ=0.99 is correct for the continuous family; the current γ=0.999 is Procgen's value and is wrong here.** The sibling project's annotation was right.

**2. IDAAC's action distribution is an unbounded diagonal Gaussian with state-independent, zero-initialized log-std.** The supplementary states: "We use Kostrikov (2018)'s implementation of PPO ... on top of which all our methods are build." Kostrikov's `a2c_ppo_acktr/distributions.py` implements `DiagGaussian` as `self.fc_mean = init_(nn.Linear(...))` plus `self.logstd = AddBias(torch.zeros(num_outputs))` — a learned bias initialized to zero, i.e. σ₀=1.0, state-independent, NO tanh squashing. `FixedNormal.log_probs` sums over action dims (`.sum(-1, keepdim=True)`); `.entropy()` sums over dims; `.mode()` returns the mean. This is the answer to the fact the project most wanted: **IDAAC Appendix E used an unbounded Normal with summed log-prob/entropy and no squashing.** Entropy coefficient 0.0 corroborates this reading — with no squashing and a state-independent std that can shrink freely, an entropy bonus is not needed to prevent premature collapse the way it is with a state-dependent head.

**3. A continuous PPG implementation exists (XuanCe `Gaussian_PPG`) but is NOT validated on continuous control.** XuanCe (agi-brain/xuance) lists PPG as supporting both discrete and continuous action spaces and ships a Gaussian policy family; its continuous configs use `activation_action: 'tanh'` (confirmed for the analogous PPO MuJoCo config: `policy: "Gaussian_AC"`, `activation_action: 'tanh'`, `gamma: 0.99`, `gae_lambda: 0.95`, `horizon_size: 256`, `parallels: 16`, `n_minibatch: 8`, `learning_rate: 0.0004`). However, XuanCe's benchmarking paper (arXiv 2312.16248) evaluated its algorithms on MuJoCo, Atari and SMAC, and **PPG does not appear among the reported continuous-control results** — the only runnable PPG demo shown is discrete CartPole-v1. So XuanCe PPG-continuous is an *existing* implementation, not a *validated* one. The suspected tanh-without-log-det-Jacobian defect could not be confirmed or refuted from available sources and remains OPEN; because XuanCe tanh-squashes continuous actions, if the Jacobian correction is missing the log-probs are those of the pre-squash Normal and the PPO importance ratio is subtly wrong. **This means XuanCe can serve as a structural/differential reference for the auxiliary-phase mechanics but NOT as a correctness oracle for the squashed log-prob.**

**4. DI-engine PPG is a confirmed false positive for our purposes.** DI-engine's docs claim "PPG supports both discrete and continuous action spaces" and its model docstring describes emitting "the mu and sigma of the Gaussian distribution." But the visible code path uses `ppg_joint_error` and a commented reference implementation computing `F.kl_div(action_logprobs, old_action_probs, reduction='batchmean')` — which, given F.kl_div's convention (target expected as probabilities unless log_target=True), is not a correctly-formed KL, and the committed demos are Pong (discrete). The documentation's continuous claim is not backed by an exercised continuous code path. **Documenting this as a trap is worth as much as a true positive: do not treat DI-engine's docstring as evidence a continuous PPG "exists."**

**5. No continuous IBAC-SNI or CTRL implementation exists in any source searched.** IBAC-SNI's only public code is microsoft/IBAC-SNI (CoinRun/Multiroom, discrete). CTRL's only public code is bmazoure/ctrl_public (Procgen, discrete, built on Kostrikov PPO + DAAC). Both are original ports with no reference. See the searches-run appendix for the negative-result list.

**6. CTRL's SSL loss has no PPO-weighting coefficient in the paper.** The ICLR 2022 paper (Mazoure et al., arXiv 2106.02193) states "Encoder φ and auxiliary predictors used by CTRL are then updated using LCTRL = Lclust + Lpred's gradients" — the SSL loss is applied to the **encoder only** as a plain sum of two terms, with the policy head updated by the separate PPO loss. bmazoure/ctrl_public's `train_ppo.py` imports `update_ppo`, `update_daac`, and `update_cluster` as **separate update functions**, confirming a separate-phase structure, not a single weighted sum. **The project's invented `ctrl_coef = 0.1` weighting the SSL loss against PPO is therefore structurally wrong — there is no such scalar in the method.** The paper uses 200 clusters and subsamples T=2 timesteps per trajectory; the project's "8 clusters" and "ctrl_window=8" are unsourced and ctrl_window is not the same quantity as T.

### Q2 — Adaptation, method by method

**PPG.** The auxiliary distillation loss is L_joint = L_aux + β_clone·KL[π_old ‖ π_θ]. For a Gaussian policy the correct KL is the **analytic closed-form diagonal-Gaussian KL** (available in torch as `torch.distributions.kl_divergence(Normal, Normal)`), in the direction **KL(π_old ‖ π_θ)** as in Cobbe's L_joint — π_old is the reference, π_θ is being pulled toward it. Verify XuanCe implements this direction; if it computes `new_dist.kl_divergence(old_dist)` that is KL(π_new ‖ π_old), the reverse direction, which is a different (mode-seeking) objective and should be corrected to match Cobbe.
- β_clone=1: IDAAC Appendix E reports β_clone=1 for continuous PPG; XuanCe uses 2.0 (MuJoCo) / 1.0 (Box2D). **Adopt β_clone=1** — it is the value the authors' own continuous grid search selected, and it is the safest anchor. Note that unlike a categorical KL over a small discrete set, a Gaussian KL is unbounded, so β_clone matters more; keep gradient clipping on (see below) to contain it.
- Gradient clipping: Cobbe's released PPG has none. For continuous control this is unsafe because the surrogate and the Gaussian KL can blow up; XuanCe's PPO config uses `clipgrad_norm: 0.5`. **Add global-norm gradient clipping (0.5) for the continuous port** — this is a defensible deviation, not a divergence from the method.
- Auxiliary cadence anchor: per Cobbe et al. (2021, "Phasic Policy Gradient"), the standard PPG setting is "E_aux = 6 while E_π = E_V = 1," and the paper notes "training with a single policy epoch is almost always optimal or near-optimal in PPG" — so E_π=1, E_aux=6 (matching IDAAC's Appendix E continuous PPG) is well-grounded.
- Squashed policy KL: if tanh-squashing is used, compute the auxiliary KL on the **pre-squash Normal parameters** (the tanh is a deterministic bijection, so the distillation target is well-defined on the base distribution and the analytic Gaussian KL applies). **Simpler and more defensible: follow IDAAC and use an UNBOUNDED Normal with no squash**, matching the authors' own continuous configuration, which sidesteps the Jacobian issue entirely.

**IBAC-SNI.** Eq. 7: G^SNI = λ·G_AC(π̄^r, π̄, V̄) + (1−λ)·G_AC(π̄^r, π̄, V̄) — the critic is always the deterministic V̄; SNI mixes only the policy gradient's stochasticity. Verified against the paper (Igl et al., NeurIPS 2019, arXiv 1910.12911): the deterministic pass suspends the injected VIB noise, and §4 states SNI's "goal is to allow us to make use of such techniques while mitigating the adverse effects the added stochasticity can have on the RL gradient computation."
- Two noise sources after porting: the VIB latent bottleneck (original) and the Gaussian action distribution (new). **The "deterministic" pass should fix the VIB latent (use the posterior mean, no ε sampling), NOT the action distribution.** The action stochasticity is intrinsic to a stochastic policy and is what the PPO ratio is defined over; SNI was only ever about the *regularizer's added* noise ("the added stochasticity"), not the policy's own exploration noise. Fixing the action distribution would change what algorithm you are running. This is the defensible derivation and it follows the authors' reasoning.
- The released code implements λ ∈ {0, 0.5, 1}, and λ=1 goes through a distinct L2-on-activations path (`--beta-l2a`) that the paper notes is mathematically distinct from the VIB-KL used at λ<1. **A continuous port should offer λ=0.5** — the authors' best, confirmed verbatim in the microsoft/IBAC-SNI README run command: `--run-id ibac-sni-lambda0.5 ... --l2 0.0001 -uda 1 --beta 0.0001 --nr-samples 12 --sni` — and treat λ=1 as a separate ablation, not a continuous knob.
- β (VIB coefficient) is per-benchmark (1e-3 toy / 1e-6 Multiroom / 1e-4 CoinRun). There is no principled closed-form rule; it is empirical. **Cheapest defensible rule: adopt β=1e-4, the CoinRun value** — CoinRun is the closest analogue (pixel-based, generalization-focused) and is the value IDAAC's authors themselves reused ("IBAC-SNI λ = .5 ... β = .0001" in the IDAAC supplementary). If instrumented, target a small, non-collapsing KL(z|o ‖ prior) of order 0.1–1 nat/step and adjust β by a factor of 10 only if the bottleneck KL collapses to ~0 (β too high) or fails to compress (β too low).
- Adjacent precedent: InfoBot (Goyal et al., "InfoBot: Transfer and exploration via the information bottleneck," ICLR 2019) and its follow-up Variational Bandwidth Bottleneck (Goyal et al., arXiv 2004.11935, which evaluated β ∈ {0.001, 0.005, 0.009, 0.01, 0.09}) use β in the ~1e-3 range for information-bottleneck RL policies, consistent with adopting β=1e-4 as a conservative anchor.

**CTRL.** L_CTRL = L_clust + L_pred, encoder-only, plain sum (no PPO-weighting coefficient — the invented ctrl_coef=0.1 is structurally wrong; remove it and update the encoder in a separate step as bmazoure/ctrl_public does with `update_cluster`).
- 200 clusters vs the project's 8: SwAV-style online Sinkhorn clustering normalizes over the batch and enforces equipartition, so **cluster count must be small relative to batch size or the equipartition constraint forces near-empty clusters and collapse.** Per SwAV (Caron et al., arXiv 2006.09882): "Throughout the paper, we train SwAV with 3000 prototypes" trained "with stochastic gradient descent using large batches of 4096 different instances" (batch ≈ 1.4× prototypes), and the paper notes the number of prototypes "has little influence as long as there are 'enough.'" The SwAV README makes the collapse mechanism explicit: with small batches, "the only valid assignment that satisfy the equipartition constraint ... is the uniform assignment (1/K where K is the number of prototypes)," and it therefore adds a queue (e.g. `--queue_length 3840 --epoch_queue_starts 15` for batch 32) to raise the effective sample count. CTRL's 200 clusters presuppose a rollout of thousands of trajectory views. **At our batch (num_steps 2048, T subsampled) the defensible cluster count is far below 200** — order 16–32 — and even that only works if the Sinkhorn is computed over the whole rollout, not an 8-step window.
- Sinkhorn collapse at small batch: SwAV's README workaround is to "use a lower epsilon value (--epsilon 0.03 instead of the default 0.05)," and the paper freezes prototypes early ("To help the very beginning of the optimization, we freeze the prototypes during the first epoch of training"). **Collapse diagnostic: cluster-assignment entropy / effective number of clusters (exp of assignment entropy). Health = assignments spread across most clusters (effective count ≈ cluster count); failure = mass concentrating on one or two clusters (effective count → 1).** This is readable within the first few updates.

**IDAAC (ported, same questions apply).**
- Instance-invariance loss arithmetic: the discriminator predicts trajectory ORDER from paired same-level embeddings (si, sj). With num_steps=2048 in one episode-spanning rollout, usable ordered pairs are drawn from within the rollout; at 256 steps in a single half-episode the pairs are all from one scene at nearby timesteps — the discriminator has almost nothing to discriminate.
- **CRITICAL fixed-horizon / single-scene assessment:** (i) The instance-invariance/adversarial component is designed to *remove level-identity information* from the value-relevant representation. With ONE training scene there is no level identity to remove — the loss becomes degenerate (the discriminator's task reduces to ordering timesteps within one scene, which is exactly the time-remaining signal DAAC wants to *keep out* of the policy). It is at best a no-op and at worst actively harmful. (ii) DAAC's value-decoupling rationale rests on the paper's observation (Appendix F/G, verified: "the value loss is positively correlated with the test score") across *procedurally generated* levels because the value must encode level-specific length/difficulty. **With a fixed horizon of 500 and no early termination, the value function's time-dependence is a clean, shared linear ramp — there is no level-specific length to leak, so the central premise of the decoupling argument does not hold in our setting.** IDAAC/DAAC can still run, but the mechanism they are named for is largely inert here. This is the strongest scientific caveat of the four arms.

### Q3 — The rollout verdict (concrete numbers)

Published rollouts per update: PPG 65,536; IDAAC Procgen 16,384; IDAAC Appendix E continuous **2,048 (1 process)**; CTRL 8,192; ours **256 with 8-sample minibatches**.

- **What matters more, total samples or parallel envs?** Andrychowicz et al. ("What Matters in On-Policy RL") find batch size is what controls the achievable step size — "larger batch sizes admit higher step sizes without plateauing, whereas smaller batch sizes are very susceptible to overly large steps" — and their practical recommendation is to increase the batch and go over experience multiple times. Parallel envs matter mainly as a route to a bigger, more *decorrelated* batch; the decorrelation is secondary to raw batch size for PPO-family stability. **Therefore fix the problem by raising num_steps, which is free under our constraints, rather than building subprocess parallelism.**
- **IDAAC's 2048×1-process config directly legitimizes num_envs=1 for IDAAC/DAAC and PPG** (the authors ran exactly this). It does NOT automatically legitimize it for CTRL, whose Sinkhorn clustering wants many decorrelated trajectory views per batch — a single long rollout gives correlated, temporally-adjacent views.
- **Budget arithmetic:** 500k frames ÷ (2048 steps) = **~244 updates**. At 10 PPO epochs × 32 minibatches = ~78,000 gradient steps. At the current 256 steps it is ~1,953 updates but with 8-sample minibatches the gradients are pure noise.
- **PPG auxiliary cadence:** with N_π=32 (from Appendix E) and 244 updates, that is only **~7 auxiliary phases in an entire run**. That is marginal but non-zero — the auxiliary distillation will do *something* measurable but should not be expected to reach its Procgen effect size. Reducing N_π to 8–16 for the continuous port (giving ~15–30 aux phases) is a defensible deviation to make the mechanism observable within budget; document it.
- **Horizon-500 interaction:** at num_steps=2048 a rollout spans ~4 complete episodes, so GAE sees genuine terminal/time-limit bootstrapping and complete return structure. At 256 it spans half an episode with **no terminal at all — every update sees only bootstrapped, non-terminal returns**, which is especially damaging for the value-decoupling methods (DAAC/IDAAC) that reason about the value's time-dependence. This is an independent reason to raise num_steps.
- **Middle options:** rollout accumulation across updates (collect several 2048-step rollouts into one update buffer) is the cleanest way to get batch statistics without parallel envs and is compatible with on-policy validity if the policy is held fixed during accumulation; this is worth considering for CTRL specifically to feed the Sinkhorn more views. Truncated-BPTT/recurrent restructuring is not worth it here.

**Concrete recommendation per arm (500k frames, 1 env, horizon 500):**

| Arm | num_steps | num_mini_batch | PPO epochs | γ | Notes |
|---|---|---|---|---|---|
| IDAAC | 2048 | 32 (→64 samples/mb) | 10 | 0.99 | Matches Appendix E exactly |
| DAAC | 2048 | 32 | 10 | 0.99 | Same |
| PPG | 2048 | 32 | E_π=1, E_aux=6 | 0.99 | N_π 8–16 (down from 32) to get enough aux phases |
| IBAC-SNI | 2048 | 32 | 3–10 | 0.99 | Follow PPO base; β=1e-4, λ=0.5 |
| CTRL | 2048 (+accumulate 2–4 rollouts for Sinkhorn) | 32 | 3–10 | 0.99 | 16–32 clusters, not 200 or 8 |

The current 256 // 32 = 8 samples per minibatch is below any published regime and is the first thing that makes numbers meaningless. **num_mini_batch=32 at num_steps=2048 gives 64 samples/minibatch, matching IDAAC's own 2048/32 = 64.**

### Q4 — Validation without published numbers

- **Procgen-first: NOT worth it.** It costs a second environment stack, a discrete action path, and a separate encoder config — real work for a robosuite-only benchmark — and it validates the discrete method, not the continuous port, which is the thing actually in doubt. Skip it.
- **Differential testing against XuanCe Gaussian_PPG on BipedalWalker/HalfCheetah/Hopper: worth doing for PPG, with a stated limitation.** It costs hours, no second benchmark stack. It **would establish** that our auxiliary-phase mechanics (buffer handling, KL direction, aux value head, β_clone application) match a reference implementation and produce comparable learning curves on a standard task. It would **NOT establish** that either implementation's tanh log-prob is correct (the suspected XuanCe Jacobian defect means both could share the same bug), nor that the method behaves correctly on 7-D pixel manipulation. So it is corroboration of structure, not proof of correctness. There are **no equivalent cheap reference targets for IBAC-SNI or CTRL** — no continuous VIB-policy baseline or SwAV-style RL encoder on continuous control with published numbers exists to diff against.
- **Cheapest credible correctness evidence = diagnostic signatures + unit tests** (below), since no published continuous score exists for three of four arms.

**Diagnostic signatures (metric / health / failure / frames to read):**
- PPG auxiliary phase: value error on held-out states before vs after the aux phase. Health = aux phase reduces held-out value MSE; failure = no change or increase. Readable after the first aux phase (~N_π updates ≈ 30–70k frames).
- IBAC-SNI λ-interpolation: run λ=0, 0.5, 1 briefly; the λ=0.5 gradient-variance and return should sit between the λ=0 and λ=1 extremes. Health = monotone interpolation; failure = λ=0.5 outside the envelope. ~50k frames each.
- CTRL cluster health: assignment-histogram entropy / effective number of clusters. Health = effective count near cluster count; failure = collapse to 1–2 clusters. Readable in the first few updates (~10k frames).
- VIB posterior: mean KL(z|o ‖ prior) per step. Health = small positive (0.1–1 nat); failure = →0 (collapse, β too high) or unbounded growth.
- Gaussian head: mean policy entropy / mean σ across the 7 dims. Health = σ decreasing smoothly from ~1.0; failure = σ saturating at a floor, exploding, or entropy collapsing in the first few updates.

**Failure modes to instrument up front:** Gaussian entropy collapse/explosion in 7-D; std saturating at the schedule floor; importance-ratio blowup (log clipfrac); VIB posterior collapse; Sinkhorn cluster collapse; IDAAC discriminator saturation (accuracy →0.5 means no signal, →1.0 means it is memorizing timestep, both degenerate in single-scene).

**Unit/property tests (no training run, highest ROI):**
- *All Gaussian arms:* analytic diagonal-Gaussian KL equals a Monte-Carlo estimate to tolerance; entropy of a 7-D diagonal Gaussian equals the closed form 0.5·Σ(1+ln(2πσ²)); log_prob sums over the 7 dims (matching Kostrikov's `.sum(-1)`); if squashing is used, log_prob includes the tanh log-det-Jacobian term Σ log(1−tanh²(u)) (this is exactly the test that catches the suspected XuanCe defect).
- *PPG:* auxiliary KL loss is exactly zero when the policy has not moved (π_old == π_θ); KL direction is KL(π_old ‖ π_θ).
- *IBAC-SNI:* at λ=1 the gradient reduces exactly to the deterministic-pass gradient; at λ=0 to the stochastic-pass gradient.
- *CTRL:* Sinkhorn output rows and columns satisfy the marginal constraints (row sums = 1/N, column sums = 1/K) to tolerance; L_clust is symmetric under swapping the two views.
- *IDAAC:* advantage-head output has the right shape; discriminator loss is finite; with one scene, assert the invariance loss is either disabled or flagged (see reportability).

### Q5 — Reportability, given dropping is off the table

**PPG.**
(a) Change list: **must-fix** — γ 0.999→0.99; num_steps 256→2048, num_mini_batch to give ≥64 samples/mb; add gradient clipping (0.5); β_clone=1; verify KL direction = KL(π_old‖π_θ). **Better** — reduce N_π to 8–16; differential-test against XuanCe on BipedalWalker.
(b) Caveat language a reviewer accepts: *"Continuous PPG following Cobbe et al.'s auxiliary-phase formulation with the continuous hyperparameters reported in Raileanu & Fergus (2021), Appendix E (N_π, E_π, E_V, E_aux=6, β_clone=1); action head an unbounded diagonal Gaussian per Kostrikov's PPO. Not validated against a published continuous PPG score; structure differential-tested against XuanCe's Gaussian_PPG."*
(c) Unreportable threshold: only if the auxiliary phase demonstrably never fires (too few updates) AND cannot be made to fire within budget — not the case at 2048 steps with reduced N_π.
(d) Still the method? Yes — a small-scale but faithful PPG.

**IDAAC/DAAC.**
(a) **must-fix** — γ 0.999→0.99; num_steps→2048 (matches Appendix E exactly); minibatches 32; 10 PPO epochs; ent coef 0.0; **decide the invariance loss** (see d). **Better** — confirm the ported action head is Kostrikov's unbounded DiagGaussian, not a squashed variant.
(b) Caveat: *"Continuous port of IDAAC/DAAC following the authors' own DMControl configuration (Raileanu & Fergus 2021, Appendix E: γ=0.99, λ=0.95, 2048 steps, 1 process, 10 PPO epochs, 32 minibatches, entropy coef 0.0, value-loss coef 0.5, linear LR decay). Trained on a single visual scene with fixed horizon 500."*
(c) **Unreportable threshold — this is the arm with a real one.** IDAAC's instance-invariance loss and DAAC's value-decoupling premise both assume multiple procedurally-generated variable-length levels. With ONE scene and a fixed horizon, the invariance loss is degenerate and the decoupling premise is largely void. **If the invariance loss is left on with one training scene, the arm is arguably running a different, ill-posed objective and is indefensible.** The fix that keeps it reportable: run DAAC (decoupling only, invariance off) as the honest instantiation, and either drop the "I" or report IDAAC with the invariance term explicitly disabled and caveated. What would settle it: an ablation showing the invariance term's gradient magnitude is negligible / the discriminator is at chance — if so, report as "IDAAC with inactive invariance term (single-scene)."
(d) Still the method? DAAC yes; full IDAAC only with the caveat that its defining component is inert in single-scene training.

**IBAC-SNI.**
(a) **must-fix** — γ→0.99; num_steps→2048; β=1e-4; λ=0.5; deterministic pass fixes the VIB latent (posterior mean), not the action distribution. **Better** — instrument VIB KL to confirm the bottleneck is active.
(b) Caveat: *"Original continuous adaptation of IBAC-SNI (Igl et al. 2019); no continuous reference implementation exists. VIB coefficient β=1e-4 and λ=0.5 taken from the authors' best CoinRun configuration; SNI's deterministic pass applied to the VIB latent only. Unvalidated."*
(c) Unreportable threshold: if the VIB bottleneck collapses (KL→0) for all defensible β and cannot be made active, the "IB" in IBAC-SNI is absent and the arm is a plain PPO with SNI noise mixing — report only if the bottleneck can be shown active.
(d) Still the method? Only if the bottleneck is active and the deterministic pass is on the latent; otherwise it is a differently-named PPO variant.

**CTRL.**
(a) **must-fix** — remove the invented ctrl_coef=0.1 (no such scalar; encoder updated separately as L_clust+L_pred); γ→0.99; num_steps→2048 (accumulate 2–4 rollouts for the Sinkhorn if collapse is observed); cluster count 16–32, not 200 or 8; drop "ctrl_window=8" (not the same quantity as the paper's T; use T=2 subsampled timesteps per trajectory as in the paper). **Better** — lower Sinkhorn ε to ~0.03 and freeze prototypes for the first updates (SwAV guidance).
(b) Caveat: *"Original continuous adaptation of CTRL (Mazoure et al. 2022); no continuous reference implementation exists. Encoder-only SSL loss L_clust+L_pred per the paper; cluster count reduced from 200 to [16–32] to match the reduced batch size; unvalidated."*
(c) **Unreportable threshold — second real one.** If the Sinkhorn clustering collapses (effective cluster count →1) at the achievable batch size and cannot be rescued by rollout accumulation / fewer clusters, the SSL loss is inert and the arm is plain PPO wearing CTRL's name. Report only if cluster health can be demonstrated (effective-count diagnostic).
(d) Still the method? Only if clusters do not collapse; the invented ctrl_coef and 8-cluster/8-window settings as-run are NOT CTRL.

**Defensible framing for all four (precedent-backed):** report the eight off-policy/verifiable arms in the main table, and the four on-policy ports in a **clearly-labelled separate block titled "Unvalidated continuous adaptations,"** with a limitations paragraph stating that PPG has a third-party continuous reference (unvalidated), IDAAC/DAAC follow the authors' own DMControl config but with single-scene caveats, and IBAC-SNI/CTRL are original ports with no reference. Benchmark papers commonly separate "reproduced" from "as-reported" or "our reimplementation" rows; the RL-generalization literature (e.g., the Procgen-era benchmark tables) routinely flags reimplemented baselines. This preserves twelve rows without overclaiming. **The honest bottom line: PPG and DAAC are reportable with modest caveats; full IDAAC and CTRL are reportable only if their defining mechanisms can be shown to be active in our regime, and IBAC-SNI only if its bottleneck is active — those three carry the renegotiation risk, and the diagnostics above are what settle each.**

## Recommendations

1. **Immediately (no training):** change γ to 0.99 for the on-policy family; change num_steps to 2048 and num_mini_batch to 32; delete ctrl_coef, the 8-cluster and ctrl_window=8 values. Write the unit/property tests (Gaussian KL vs Monte-Carlo, entropy closed form, log-prob dim-summing, Sinkhorn marginals, PPG zero-KL-when-static, SNI λ-limits). These catch the highest-cost defects for zero T4 hours.
2. **First cheap runs:** differential-test continuous PPG against XuanCe `Gaussian_PPG` on BipedalWalker-v3 (hours). Instrument all five diagnostic signatures on short (~50k-frame) runs of each arm.
3. **Decision gates:** IDAAC → if discriminator is at chance in single-scene, report as "DAAC / IDAAC with inactive invariance term."
