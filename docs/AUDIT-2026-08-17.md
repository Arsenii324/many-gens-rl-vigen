## Question 1: Were training or evaluation harnesses merged?

**No training harness was merged.** Each baseline is launched through its own entry point, and that is checkable rather than asserted:

| Baseline | Entry point — the authors' | Loop, buffer, logger, eval |
|---|---|---|
| rad, soda | `dmc_gb/src/train.py` | theirs, unmodified control flow |
| alda | `alda/scripts/train.py` + its own spec mechanism | theirs |
| ppg | `python -m phasic_policy_gradient.train` | theirs |
| idaac | `idaac/train.py` | theirs |
| ibac_sni | `torch_rl/scripts/train.py` | theirs |
| ctrl | `ctrl/train_ppo.py` | theirs (JAX) |
| drqv2, svea, sgqn, curl, drq | `RL-ViGen/train.py` — which *is* their original | theirs |

Seven distinct training loops for twelve baselines, which is the number the references themselves ship: RL-ViGen shares one loop across its own five, and `dmc_gb` shares one across `rad` and `soda`. That sharing is the authors', not ours.

### Evaluation, where there is one real exception

- **Ten baselines evaluate through their own code.** Success-rate accumulation was added *inside* each repo's existing eval loop; no loop was replaced.
- **`ibac_sni` uses its own `scripts/evaluate.py`** to measure a saved policy in a held-out regime — the same one-line env seam as its `train.py`, 6 added lines, no evaluation loop authored.
- **`ppg` is the exception.** It ships no evaluation entry point at all — `train.py` trains, `graph.py` plots CSVs, and the only `load` in the package is a comment. `runnable/_launch/ppg_eval.py` is therefore ours. It lives *outside* the clone (zero deviations on the ledger) and reuses everything that could bias a number: `get_venv`, their `Roller`, their `VecMonitor2`, their `PpoModel.act`. Ours is the loop that stops after N episodes.
- `scripts/collect_metrics.py` reads six log formats into one record shape. It is a *reader*: it runs nothing and cannot change a number.

> [!NOTE]
> **The one harness that was merged is the one we abandoned.** The superseded `rlgen/` port had a single shared trainer, evaluator and logger for all twelve. That is precisely the design this approach replaced, and it is still on disk, measured, and labelled superseded in `docs/STATE-2026-08-16.md`.

## Question 2: Was anything removed, or only partially ported?

**Nothing was removed and nothing is partial.** Each clone is the complete original repository with a `PRISTINE:` first commit, so `git diff` against it is the exhaustive statement. Two mechanical checks:

- **Zero deleted files** across all six clones (`grep "deleted file"` over every exported patch returns nothing).
- **117 removed lines total**, and every one is a replacement-in-place, not a deletion. Read verbatim, they fall into five kinds:

| Kind | Example (the − line) | Replaced by |
|---|---|---|
| Signature widened | `obs, reward, done, _ = env.step(action)` | same call, capturing `info` |
| Version drift | `jax.ops.index_add(...)`, `jax.tree_multimap`, `.copy(add_or_replace=)` | documented successors, same semantics |
| Env construction wrapped | `env = ProcgenVecEnvCustom(..., num_levels=200, ...)` | a branch whose Procgen arm passes *identical* arguments |
| Discrete → continuous | `pi = tfd.Categorical(logits=logits)` | `self.make_pi(logits)`, Categorical on the discrete path |
| Placeholder filled | `"/your/data/path/here/"` | a relative path the repo can resolve |

The removals that look largest — `ctrl`'s 58 lines — are almost entirely the three `ProcgenVecEnvCustom` blocks being folded into one factory. Its Procgen arm reconstructs them argument-for-argument (`mode='easy'`, `paint_vel_info=False`, `normalize_rewards=True`), so the original path is preserved exactly.

The *superseded* `rlgen/` port is a different story and its removals are recorded in `docs/STATE-2026-08-16.md` — launcher, logger and env layers cut from every vendored base, plus two undeclared ones found on 2026-08-16 (`NNBase` inlined; `LinearOrderClassifier` hand-rewritten from a docstring while the reference sat ten lines away). That is exactly the failure mode the clone approach removes: with a full clone there is nothing to forget to port.

## Question 3: Were the algorithms deviated — including parameters?

### Scalar hyperparameters: none changed, and this part is verifiable

Every argument the launchers pass is env selection, parallelism, logging, or protocol. Grepping all seven launchers for `lr`, `entropy_coef`, `clip_param`, `batch_size`, `gamma`, `gae`, `epochs` returns **nothing**. Each repo runs on its own defaults.

ALDA is the case worth checking hardest, because it is configured by a file we added. Diffing our `train_alda_robosuite_door.yaml` against the repo's own `train_alda_ball_in_cup_catch.yaml`, with task names normalised, the *entire* difference is:

```yaml
  action_repeat: 4   ->  1        (protocol; RL-ViGen's own Table 2 says 1 for robosuite)
  episode_length: 1000 -> 500     (robosuite's own horizon)
+ scene_id: 0                     (an RL-ViGen concept DMC has no equivalent for)
```

`seed`, `batch_size: 128`, `num_latents: 12`, `values_per_latent: 12`, `beta: 100`, `n_train_steps: 500_000` are all theirs, untouched.

### Algorithms: four heads, one repair, one latent-bug fix

| Change | Baseline | What it is | Provenance |
|---|---|---|---|
| Continuous policy head | idaac | `FixedNormal` + `AddBias` + `DiagGaussian` | `[copied verbatim]` from `ikostrikov/pytorch-a2c-ppo-acktr-gail@41332b7` — the file's own upstream, whose `init`/`FixedCategorical`/`Categorical` are byte-identical to idaac's |
| Continuous policy head | ppg | `_make_normal` completed | `[authored]` — upstream's body was unreachable and hardcoded `scale=1.0` under its own `warnings.warn("Using stdev=1")`. Ours clamps `log_std` to `[-5, 2]`, i.e. $\sigma \in [0.0067, 7.39]$ |
| Continuous policy head | ibac_sni | `make_dist` → `Independent(Normal, 1)` | `[authored]` — `torch_rl` raises on anything but `Discrete` |
| Continuous policy head | ctrl | `make_pi` → `MultivariateNormalDiag` | `[authored]` |
| Action conditioning | idaac, ctrl | one-hot → the real action vector, for the advantage/cluster heads | `[adaptation]` — a Box action already *is* the vector the one-hot was producing |
| MYOW loss restored | ctrl | two commented lines uncommented | `[repair]` — see below |
| `num_actions` forwarded | idaac | advantage head sized from the action space | `[latent bug]` — inert on Procgen, required here |

**All four heads initialise `log_std = 0` ($\sigma = 1$).** That is not four independent guesses: it is the value the one verbatim-copied reference uses (`AddBias(torch.zeros(num_outputs))`), applied uniformly to the three that had no continuous head to inherit from. Verified numerically rather than by inspection — logged entropy 9.9333 (ppg) and 9.935 (ibac_sni) against $7 \times \frac{1}{2}\log(2\pi e) = 9.9326$, and jax's MVNDiag reports 9.93257 for the same distribution.

> [!NOTE]
> **The one change that alters a running algorithm: `ctrl`.**
> `algo.py:203` comments out `scores_w_target = w_clust_target @ protos` while line 211 still reads `scores_w_target`. As released, `ctrl_public@7a118c8` raises `NameError` the first time `update_cluster` runs — it cannot execute its own `ppo_ctrl` at all. Restoring the authors' own two lines makes the MYOW branch live, which is a genuine change in what the loss computes versus the released file. Checked for completeness: the *online* `w_clust` is unpacked and never used again, so leaving its partner line commented changes nothing, and the restoration is minimal for the path that actually runs.

### Recorded, deliberately not fixed

- **`ppg`'s auxiliary KL is not summed over the action dimension.** `aux_train` does `td.kl_divergence(oldpd, pd).mean()` with no `sum_nonbatch`. For a Categorical that is a mean over (B,T); for a 7-dim Normal it averages over the action axis while the PPO losses sum over it, making the effective `beta_clone` $7\times$ smaller than the loss it is weighed against. It is the authors' line applied to a distribution they never used, and leaving it is the null.
- **`ctrl`'s MYOW loop ignores its own index.** `for k_idx in range(myow_k)` indexes `indx[:, 0 + 1]`; `k_idx` is never used, so every iteration draws the same nearest cluster.
- **`evaluate.py`'s `--argmax` is Categorical-only`** (`dist.probs`). Nothing uses it, and deterministic evaluation of a Gaussian means its mean, not an argmax — a decision, not a reflex.

## Question 4: The class I under-reported: format, shape, and what they propagate into

You remembered this correctly. Augmentation-based methods have an input shape their augmentation is *defined against*, and the shape is not a free variable.

### Where the sizes come from — five of seven are the reference's own

`dmc_gb` settles its own case in `src/arguments.py`:

```python
if args.algorithm in {'rad', 'curl', 'pad', 'soda'}:
    args.image_size = 100
    args.image_crop_size = 84
else:
    args.image_size = 84
```

So the 100×100 render for `rad`/`soda` is **the repo's own rule**. RL-ViGen renders 84 and offers no way to change it; patch **P6** exists so the environment can supply what the algorithm already demands. Without it, the exact failures you remember:

- **RAD silently becomes SAC.** `random_crop` computes `crop_max = img_size - size = 84 - 84 = 0` and returns the input unchanged by its own `if crop_max <= 0` guard. No error, no warning, no augmentation.
- **SODA refuses to run.** `soda.py:51` is `assert x.size(-1) == 100`.

| Baseline | Render | Whose choice | Why that size |
|---|---|---|---|
| rad, soda | 100 → crop 84 | the repo's | `arguments.py` sets it for exactly these algorithms |
| ppg | 64 | the reference's | Procgen native; `ImpalaCNN`'s dense layer derives from it, giving the same 2048 as upstream |
| idaac | 64 | the reference's | `nn.Linear(2048, hidden)` is hardcoded; 2048 = 32×8×8 holds only at 64 |
| ctrl | 64 | the reference's | `model.init` example is literally `jnp.zeros((1, L, 64, 64, 3))` |
| alda | 64 | the reference's | encoder built for 64; an 84 render dies on a 3×6400 vs 4096×256 mismatch |
| drqv2, svea, sgqn, curl, drq | 84 | the benchmark's | RL-ViGen's own default; P6 inert |
| **ibac_sni** | 64 | **ours** | its `torch_rl` branch is MiniGrid and has no image-size precedent; 64 borrowed from the paper's own CoinRun branch |

> [!WARNING]
> **And here is the network size I said we never set.** `ibac_sni` defines its width *as a function of the input*:
> ```python
> self.image_embedding_size = ((n-1)//2-2) * ((m-1)//2-2) * 64
> 
>   7x7   ->        64      (MiniGrid, what the code was written for)
>   64x64 ->    53,824      (what our choice produces)
>   84x84 ->    97,344
> ```
> That feeds `Bottleneck(self.embedding_size, 64)` — so the choice of 64×64 sets a multi-million-parameter layer where the reference had a 64-wide one. Nobody typed a network size; an input format determined one. This is the single largest architectural consequence in the project and it belongs in any comparison that treats these twelve as peers.

**Measured, not estimated** — `python scripts/probe_geometry.py` (PROBE 3) constructs the real `ACModel` at each resolution:

| input | embedding | conv params | **total params** |
|---|---|---|---|
| 7×7 — MiniGrid native, what the architecture was written for | 64 | 10,544 | **15,231** |
| **64×64 — ours** | 53,824 | 10,544 | **3,455,871** |
| 84×84 — the RL-ViGen five's, for comparison | 97,344 | 10,544 | 6,241,151 |

The conv trunk is **identical at every resolution** (10,544 parameters). Choosing 64×64 over MiniGrid's 7×7 multiplies the model by **227×**, and every added parameter sits in a fully-connected head fed by a flattened conv output the architecture expected to be 64-dimensional. The resolution *was* the layer size.

### Input scale, which is not shared either

Every baseline normalises pixels itself, and one does not:

| Baseline | Scaling | Range | Where |
|---|---|---|---|
| rad, soda | `x/255.` | [0, 1] | `modules.py:88` |
| alda | `obs.float()/255.` | [0, 1] | `alda_trainer.py:505` |
| ppg | `x/scale_ob`, `scale_ob=255` | [0, 1] | `impala_cnn.py` |
| idaac | `/255.` | [0, 1] | `envs.py:27,41` |
| ctrl | `/255.` | [0, 1] | `algo.py:176` |
| **ibac_sni** | **none upstream** — we divide in the seam | [0, 1] | `utils/general.py:66` |
| **RL-ViGen five** | `obs/255.0 - 0.5` | **[−0.5, +0.5]** | `drqv2.py:64` |

Two things there. `ibac_sni`'s `preprocess_images` does `torch.tensor(images, dtype=torch.float)` with *no* division — correct for MiniGrid, whose "image" is small category indices, and two orders of magnitude wrong for RGB. The division is ours, placed in the seam rather than in their preprocessor, and it is a real decision about input scale. And RL-ViGen's own five centre their input at zero while the other seven do not — inherited, not ours, and still a difference between the twelve.

### Output shape

Discrete 15 → `Box(-1,1,(7,))` forced the heads above, and one derived width: IDAAC's advantage head is `nn.Linear(hidden_size + num_actions, 1)`, so 256+15 becomes 256+7. That head previously received a hardcoded default of 15 because `num_actions` was never forwarded into the base — right for Procgen, silently wrong for anything else.

## Question 5: Is this good for both CUDA and MPS?

**CUDA is the primary path and no source line was changed for MPS.** Device adaptation lives entirely in `runnable/_shim/sitecustomize.py`, loaded via `PYTHONPATH`, changing zero repo lines. The alternative was patching `.cuda()` at 22 call sites across 7 files in `dmc_gb` alone — 22 authored deviations bought purely for local convenience.

Evidence for CUDA is direct, not inferred: RAD trained on a real Tesla T4 across six kernel runs with `runnable/_shim` *absent* from `PYTHONPATH`, on clones rebuilt from public GitHub at the pinned SHAs by our own exported patches, with `apply_patches.py --check` exiting 0 on a machine that had never seen this workspace. The log also shows `Observations: (9,100,100)` → `Cropped: (9,84,84)`, which proves P6 is live there and that RAD is genuinely RAD.

| Where they differ | MPS | CUDA | Consequence |
|---|---|---|---|
| float64 | does not exist; shim downcasts to float32, announced once | kept | a real numerical difference; local runs are not bit-comparable to remote |
| `curl` | fails: `scatter: index -1` in its contrastive loss | expected fine | run it with `device=cpu` locally; isolated by re-running, not assumed |
| DataLoader workers | MuJoCo GL dies across `fork`; workers set to 0 | fine | data-loading concurrency only; changes no number |
| Determinism | — | GPU nondeterminism observed run-to-run | same seed, same first eval; losses diverge slightly by the second update |

> [!NOTE]
> **The platform constraint that decides where real runs go.** RL-ViGen's texture modder reads `MjModel.tex_rgb`, removed in mujoco 3.0, so every `eval-*` regime needs mujoco 2.x. The last 2.x release with wheels is 2.3.7, and it stops at **cp311**. Kaggle runs **python 3.12**. So Kaggle can run the *train* regime only — enough for a CUDA smoke, useless for a generalisation benchmark. DataSphere pins 3.11; `compute/datasphere/` is prepared and asserts both `MjData.qM` and `MjModel.tex_rgb` in its first lines. It needs a project id from the console, which there is no headless way to obtain.

## Question 7: Metrics — what the sibling projects already built

Three parallel surveys over the sibling projects, each with a bounded read scope and its own output file. Together they name **577 distinct metrics**. This project currently reports two.

| Project | Names | What it is strongest at |
|---|---|---|
| `gen-rebuttal` | 253 | **Most relevant — it ported these same baselines.** Rollout health, gradient/param norms per module, latent and discriminator probes, ALDA reconstruction metrics, cross-field invariant checks |
| `flow` | 191 | A tiered diagnostic taxonomy (tier0 action stats → tier1 policy entropy → tier2 advantage/value), representation probes, explicit train−eval difference metrics |
| `unified-bench` | 133 | **The evaluation-protocol layer**: rliable IQM with stratified bootstrap CI, Wilson intervals on success rates, SEM, percentiles — and documented conditions under which each is invalid |

### Four that answer questions this audit left open

Not a wish list — each of these *measures* something I could otherwise only argue about:

- `obs/interframe_absdiff` `[gen-rebuttal]` — how much consecutive stacked frames differ. This turns the frame-stack finding from an argument into a number: it directly measures whether a stacked observation carries motion, which is exactly what separates the 8 stacked baselines from the 4 single-frame ones.
- `act/saturation_frac`, `actor/mu_saturated_frac` `[gen-rebuttal]` — the fraction of actions on the box boundary. This is the measurement of the clipped-Gaussian family's defect: how much probability mass the env is folding onto the boundary while the policy's likelihood still treats it as interior. My own superseded `rlgen/tags.py` already declared `diag/action_saturated_frac`, and it was lost when the approach changed.
- `init/pi_entropy`, `init/pi_log_std_mean` `[gen-rebuttal]` — exactly the hand-check I ran on the four authored heads (entropy 9.9333 vs $7\times\frac{1}{2}\log 2\pi e$). It should be an assertion at startup, not something a person notices in a log.
- `wilson_lo` / `wilson_hi` `[unified-bench]` — the correct interval for a binary success rate, which is the metric this project just added and currently reports as a bare point estimate.

### On family-specific metrics — my view

The twelve split into three families, and the split is the same one that keeps appearing in this audit:

| Family | Baselines | Metrics that mean something | Metrics that do not |
|---|---|---|---|
| **Off-policy actor-critic** | rad, soda, alda, drqv2, svea, sgqn, curl, drq | `critic/q_mean`, `alpha`, target-entropy tracking, buffer health (`buf/frac_full`, `buf/evicted`), update-to-data ratio | `approx_kl`, `clipfrac`, `explained_variance` — no PPO ratio exists |
| **On-policy PPO family** | ppg, idaac, ibac_sni, ctrl | `approx_kl`, `clipfrac`, `explained_variance`, advantage mean/std pre-norm, GAE diagnostics | buffer health — there is no replay buffer |
| **Method-specific** | — | idaac: `adv_head/corr`, order-classifier accuracy · ppg: aux-phase `pol_distance` · ctrl: cluster/proto entropy, dead-code fraction · alda: `recon_mse`, codebook usage · ibac_sni: bottleneck KL | meaningless across families — never aggregate them |

So the shape I would argue for is **three tiers, not one table**:

1. **Comparable across all twelve** — success rate with a Wilson interval, episode return, episode length, frames. This is the only tier that may go into one plot, and even here return is scale-arbitrary while success rate is not.
2. **Comparable within a family** — the PPO diagnostics for the four, the actor-critic diagnostics for the eight. Reported side by side, never pooled.
3. **Per-method, and reported only against itself** — a method's own mechanism working or not. These are the ones that catch a port being subtly wrong, which is exactly what this project needs and what neither of the first two tiers can see.

> [!IMPORTANT]
> **The caveats are the most valuable thing the surveys returned.**
> `unified-bench` documents ten conditions under which its own metrics are invalid — IQM truncation artifacts on near-binary rewards, single-run SEM being pure Bernoulli noise, single-seed point estimates being statistically unreliable, level contamination between train and eval. Adopting the metric without the caveat would be adopting the failure. That is the part to port first.

### What is implemented, as of now — not proposed

`scripts/metrics.py`, 38 property-based tests in `tests/test_metrics.py`, plus a module `--self-test`. Each carries its conditions of validity in its docstring, because the caveat is the part that gets dropped.

| Metric | Why this one, over the obvious alternative |
|---|---|
| `wilson_interval` | Every success rate we report is **0.000**. The normal approximation has width *zero* at p=0, which reads as having proven the policies never succeed, from ten episodes. Wilson gives `[0.000, 0.278]`. |
| `iqm` + `bootstrap_ci` | Robust to outlier episodes — carrying `unified-bench`'s own caveat that on a near-binary reward IQM truncates the signal away. |
| `interframe_absdiff` | Turns the frame-stack argument into a number. Returns 0.0 for a single frame meaning *NOT MEASURABLE*, never "no motion". |
| `action_saturation_frac` | Finding 6, quantified. **Measured 31.8%** for the four unsquashed heads at initialisation, 0.0% for SAC, 5.5% for DrQv2 — and checked against the closed form $2(1-\Phi(1)) = 0.3173$. |
| `explained_variance` | Returns **nan** on constant returns, not 0.0 — 0.0 reads as "explains nothing", a different claim, and an all-zero-return batch is routine on a sparse reward. |
| `approx_kl` | Defaults to **k3**. TorchRL computes k1 only, and k1 *can go negative* — unusable as a trigger, and it invites someone to "fix" the sign. Pinned by a test where k1 is negative and k3 is not. |
| `clip_fraction`, `effective_sample_size` | Take the *log* ratio, because that is what a policy produces and exponentiating early loses precision exactly where the ratio is extreme — the region these exist to count. |
| `target_network_divergence` | Measured **nowhere in TorchRL**. It is what would have caught the DDPG defect they shipped, where `delay_value` defaulted `False` so `SoftUpdate` copied the source onto itself. |
| `diag_gaussian_entropy` | Lets a head's initialisation be *asserted* rather than noticed in a log. |

And two probes that run the measurement rather than defining it: `scripts/probe_geometry.py` (the two numbers above, self-checked against closed form) and `scripts/probe_heads.py`, which **constructs all four authored heads** — each in its own interpreter with its own `sys.path`, because importing them into one process is exactly the join this project avoids — and confirms every one reports **9.93257** against a target of $7 \times \frac{1}{2}\log(2\pi e)$. A SKIP is reported as a SKIP and never as a pass.

## Question 8: What I would do next, in order

## Question 9: What survived being checked by people who had not read this

Everything above was written by the same author who made the changes. So it was checked two ways, both deliberately blind: a subagent that recovered this project's *own* recorded failure categories and looked for live instances of each, and fifteen library sweeps asking what the established RL libraries actually do. **None of them read this report.** A reviewer who has read the report tends to confirm it; the cost of blindness is that they occasionally re-derive something already known, which is cheap, and the benefit is that agreement means something.

### And one thing the blind audit got wrong, which is why blind is not the same as right

> [!WARNING]
> It reported that "every current clone zeroes the bootstrap at the 500-step horizon." Not true. `runnable/dmc_gb/src/train.py:174` reads `done_bool = 0 if episode_step + 1 == env._max_episode_steps else float(done)` — **`rad` and `soda` handle the time limit correctly** and bootstrap through it. The other eight do not (RL-ViGen's `discount = 0.0`, `ctrl`'s `(1 - done[t])`, `idaac`'s masks, `ppg`'s `notlast`). The finding survives — a hashed protocol field claims `truncate_with_bootstrap` that most runs do not have — but it is **not uniform**, and the non-uniformity is the more interesting fact: two baselines' value targets mean something different from the other ten's, and that is declared nowhere. Earlier in the same session a blind run also invented a method name that does not exist. Verify, then repeat.

### What fifteen libraries say about the two decisions that had no reference

**The authored continuous head is not an improvisation — it is the field's standard for the on-policy family.** A trainable state-independent `log_std` initialised to 0 ($\sigma = 1$) is what SB3, Tianshou, CleanRL, PureJaxRL, garage, AgileRL and SKRL all do, and PyTorch's own library ships it as a named class — `AddStateIndependentNormalScale`, `init_value=0.0`, `scale_mapping="exp"`, used by *every* on-policy MuJoCo actor in TorchRL.

**Env-side clipping is the correct framing, and the bug is scoring the clipped action.** TorchRL's `knowledge_base/DEBUGGING_RL.md` states it directly: the clip "should be thought of as part of the environment," and the error is training on the clipped action rather than the raw one. Our four heads score the raw action, so the log-prob is self-consistent. **SKRL gets this wrong** — it stores the clipped action and takes its density under the unclipped Normal, in its own shipped manipulation examples, undocumented. Finding 6 is not hypothetical; it is live in a maintained library.

### The strongest external evidence for "any join carries a burden of proof"

TorchRL is the most direct counter-example to this project's stance — a modular library where algorithms share objectives, collectors, replay buffers and modules. Asked whether sharing has ever *silently* changed an algorithm's behaviour there, its own issue tracker answers yes about twenty times:

- **Issue #1662** — the shared value estimators read `terminated` from the `done` key, so **every algorithm using GAE or TD($\lambda$) bootstrapped as if truncations were terminations.** Nothing crashed. That is this report's own truncation finding, in the field's flagship library, as a two-line diff.
- **PR #3679** — the shared `PPOTrainer` shipped `gamma=0.9` and an *inverted* `lmbda`, while the *duplicated* script had the right values all along. The join was wrong; the duplicate was right.
- **Issue #4063** — moving a hand-written PPO loop onto the shared trainer recomputes GAE against a moved critic, a choice "selected implicitly by the hook placement"; migrating "can otherwise silently change the training semantics."

And why none of it was caught: their objectives benchmarks are 1389 lines with **zero assertions**, and their 25,275-line test suite compares TorchRL against TorchRL — which is exactly why #1662 stayed green, because *both* code paths shared the misinterpretation. Meanwhile TorchRL's own recipes duplicate rather than join ("each example is independent of each other for the sake of simplicity"), with nine identically-named helpers reimplemented across eight `utils.py` files.

> [!NOTE]
> **Two premises worth correcting.** SKRL *removed* robosuite support in v2.0.0, and even its old wrapper flattened observations to 1-D — pixel robosuite was never possible there, so the one library that looked like a shortcut is not one. And SB3's fidelity claim is narrower than its reputation: it validates against SB2 and one paper's PyBullet table, and its Zoo says of its own benchmark, "this is not a quantitative benchmark as it corresponds to only one run." Across all fifteen libraries, **nine of the twelve baselines have no implementation anywhere**.
